SaaS Identity: OAuth & OIDC

Module 12 Direct · Programmatic · Delegated OAuth · OIDC
In this note
  • Three ways into a SaaS app: direct, programmatic, and delegated — the spine of this note
  • Direct: a human logs in — password → session cookie
  • Programmatic: a script uses an API key — and why a leaked key is so dangerous
  • Delegated (an app acts for you): authorization via OAuth, and authentication via OIDC
How this differs from the Identity Security layer
In the Identity Security module you saw enterprise SSO: a workforce identity provider (Okta, Azure AD) logs you in once and authenticates you to many apps — it answers who you are. SaaS adds a need SSO was never built for: letting one app act for you — call another app’s API on your behalf, scoped, without sharing your credentials. That’s the third access type below: delegated.

1 Direct access: you log in

The simplest way in: a human types a password. The app verifies it once and hands your browser a session cookie so you don’t re-type it on every click. Toggle the two moments:

Password once, then a cookie

Authentication vs. authorization
Two different questions, and they come back later. Authentication (AuthN) — are you who you say you are? (your ID badge at login). Authorization (AuthZ) — now that you’re in, what may you do? (a keycard to a specific room).

2 Programmatic access: API keys

A session cookie is for a human in a browser. A program — a script calling a SaaS app’s API — has no browser and no login screen, so it authenticates with an API key: a long-term, static credential sent on every request. See what happens if it leaks:

An API key is a master key

The trap that forces delegation
Your password and your API key are both master keys — long-term, and able to do everything you can. So when a third-party app wants your data in another app (YouTube reading your Spotify playlists), you must never hand it your password or API key. There has to be a safer way to let an app act for you — that’s delegated access.

3 Delegated access: an app acts for you

The new SaaS pattern: you let an app do something on your behalf — without handing over your master key. Two different things can be delegated, mapping onto the two questions from §1:

Two things can be delegated
Authorization — what may the app do for you? → OAuth.   Authentication — who are you? (the app delegates verifying your identity to a trusted identity provider, or IdP) → OIDC. One grants permission; the other proves identity.
3a Delegated authorization — OAuth

An app is authorized to act for you. You want YouTube to sync the playlists from your Spotify account. Instead of your Spotify password, OAuth hands YouTube a valet key — an access token scoped to just your playlists, enforced by the API. Compare:

Master key vs valet key

The handshake (Authorization Code flow)
1YouTube redirects you to Spotify and you log in + consent (“YouTube wants to read your playlists”).
2Spotify hands back a short-lived authorization code — not the token itself.
3YouTube’s server swaps that code plus its own client secret for the access token. A malicious app that grabbed the code can’t use it without the secret.
The four players · and what a scope is
The resource owner (you), the client (the app, e.g. YouTube), the authorization server (issues the token, e.g. Spotify Auth), and the resource server (the API that holds the data, e.g. the Spotify API). A scope is a coarse permission — a resource + action like playlist-read — stamped on the token and enforced by the API. (Whether it’s your playlist is a finer check the app does itself.)
3b Delegated authentication — OIDC

Now the other question: who are you? The app delegates verifying your identity to a trusted IdP — “Log in with Google.” OAuth alone can’t do this, so OIDC adds an ID token on top of it. Two tokens, two jobs — flip them:

ID token vs access token

OIDC vs SAML
Both let you log in through a third party (federated identity) — the SSO idea from the Identity module. SAML is that enterprise SSO standard: heavier XML, browser-bound, and authentication only — it can’t issue the scoped API tokens SaaS app-to-app calls need. OIDC is the modern successor: lightweight JSON / JWT (JSON Web Token), works for mobile and “Log in with Google,” and because it rides on OAuth, the same token stack does both authentication and scoped authorization.
Remember

Three ways into a SaaS app:

  • ◇ Direct — a human logs in: password → session cookie keeps you logged in
  • ◇ Programmatic — a script uses an API key (a long-term master key); never share it or your password
  • ◇ Delegated — an app acts for you, without your master key

Delegated comes in two forms:

  • ◇ OAuth = delegated authorization (what it may do) — a scoped access token (valet key) via consent → auth code → token; scopes enforced at the API
  • ◇ OIDC = delegated authentication (who you are) — an ID token (JWT of claims) on top of OAuth. SAML = enterprise/XML/authn-only; OIDC = modern/JSON/both
