1 The same idea, at cloud scale

Everything from the last note — vaults, envelope encryption — AWS runs as a service. AWS KMS (Key Management Service) manages your keys for you and is the front door to the underlying HSMs (Hardware Security Modules).

How S3 encryption really works
When S3 encrypts an object, it doesn’t hand your data to the HSM. It asks KMS for a data key (DEK), encrypts the object with it in the service, then stores the wrapped DEK beside the object. Your KMS key (the KEK) never leaves the HSM — exactly the envelope pattern, run for millions of objects.

The precise rule (so you don’t over-simplify)
The key policy is the root of trust for a key and is always required. The common default key policy delegates to IAM (the “Enable IAM permissions” statement), so in practice a user needs both the key policy to permit IAM and an IAM policy granting the action. But a key policy can also grant a principal directly with no IAM policy. AWS evaluates the key policy, IAM policies, and grants together (not in sequence), with an explicit deny always winning.
Every key use is logged — the audit trail
KMS doesn’t just control access to keys, it records every use of them. Each encrypt, decrypt, and key-management call is written to AWS CloudTrail, giving you an audit trail of who used which key, when, and whether it was allowed or denied. That log is what turns “the key is protected” into “and we can prove exactly who touched it” — essential for investigations and compliance.
Remember

AWS KMS is the managed key service and the front door to the HSMs that hold your keys; S3 and friends use it for envelope encryption — KMS hands out a wrapped DEK while the KMS key (KEK) stays in the HSM. Keys live in either AWS-managed multi-tenant HSMs (the default) or a CloudHSM single-tenant cluster you run for strict isolation. Every key carries a mandatory key policy. Unlike an S3 bucket — where an IAM policy or a bucket policy can grant access — a KMS key’s key policy is the root of trust: it must permit the access (directly, or by delegating to IAM), so you typically need both the key policy and an IAM policy, with explicit deny always winning. And reading a KMS-encrypted S3 object needs both kinds of permission at once: s3:GetObject to fetch it and kms:Decrypt to unlock it. Every key use is recorded in CloudTrail for an audit trail.
